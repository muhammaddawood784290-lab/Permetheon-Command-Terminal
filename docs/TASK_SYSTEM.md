# PCT — Task System

**Project:** Permetheon Command Terminal
**Short Name:** PCT
**Production Domain:** `pct.permetheon.com`
**Stack:** React 18+, Tailwind CSS, Express.js, MySQL
**Document Type:** Task Management Specification
**Status:** Active Development
**Version:** 1.0

---

# 1. Purpose

The Task System is the core work-management system inside PCT.

It allows the Permetheon development team to:

```text
Create Tasks
Assign Tasks
Track Progress
Set Priorities
Set Deadlines
Attach Files
Add Comments
Track Activity
Submit Work
Request Reviews
Approve Work
Request Revisions
```

The system must provide a clear lifecycle from task creation to completion.

---

# 2. Task Lifecycle

The primary lifecycle is:

```text
BACKLOG
   ↓
TODO
   ↓
IN_PROGRESS
   ↓
IN_REVIEW
   ↓
REVISION_REQUIRED
   ↓
IN_PROGRESS
   ↓
IN_REVIEW
   ↓
COMPLETED
```

Tasks may also be:

```text
BLOCKED
CANCELLED
```

depending on project requirements.

---

# 3. Task Statuses

PCT V1 uses the following statuses:

```text
BACKLOG
TODO
IN_PROGRESS
IN_REVIEW
REVISION_REQUIRED
COMPLETED
BLOCKED
CANCELLED
```

---

# 4. BACKLOG

`BACKLOG` means the task has been identified but is not yet ready for active development.

Example:

```text
New feature idea
Future optimization
Potential bug fix
Future enhancement
```

A backlog task does not necessarily have an assigned developer.

---

# 5. TODO

`TODO` means the task is ready to be worked on.

Expected:

```text
Requirements understood
Task defined
Priority assigned
Developer may be assigned
```

---

# 6. IN_PROGRESS

`IN_PROGRESS` means the assigned developer is actively working on the task.

A task should normally have:

```text
Assigned Developer
Active Project
Defined Requirements
```

---

# 7. IN_REVIEW

`IN_REVIEW` means the developer has submitted the work for review.

Typical flow:

```text
Developer
   ↓
Complete Development
   ↓
Submit for Review
   ↓
IN_REVIEW
```

The developer should not directly mark the task as `COMPLETED` when a review is required.

---

# 8. REVISION_REQUIRED

`REVISION_REQUIRED` means the reviewer found issues or requested changes.

Flow:

```text
IN_REVIEW
    ↓
REVISION_REQUIRED
    ↓
IN_PROGRESS
```

The review feedback must explain what needs to be changed.

---

# 9. COMPLETED

`COMPLETED` means the task has successfully passed its required workflow.

If review is required:

```text
IN_REVIEW
    ↓
Approved
    ↓
COMPLETED
```

---

# 10. BLOCKED

`BLOCKED` means progress cannot continue because of an external dependency or issue.

Examples:

```text
Waiting for Client
Waiting for API
Waiting for Design
Waiting for Credentials
Waiting for Another Task
Technical Blocker
```

A blocked task should have a reason.

---

# 11. CANCELLED

`CANCELLED` means the task will no longer be completed.

Cancellation should normally require appropriate permission.

A cancelled task should remain in historical records.

---

# 14. Task ID

Every task must have a unique identifier.

Example:

```text
Task #1042
```

The ID should be generated by the backend/database.

Users must not manually choose database IDs.

---

# 15. Task Title

Task titles should be:

```text
Clear
Short
Action-oriented
Specific
```

Good:

```text
Implement Developer Login
Fix Project Dashboard Loading
Create Task Review Component
```

Avoid:

```text
Fix stuff
Website work
Important
Do this
```

---

# 16. Task Description

The description should explain:

```text
What needs to be done
Why it needs to be done
Expected result
Relevant requirements
Important constraints
```

For complex tasks:

```text
Goal
Requirements
Acceptance Criteria
Notes
```

may be used.

---

# 17. Acceptance Criteria

Tasks may define explicit acceptance criteria.

Example:

```text
Acceptance Criteria

[ ] Login form works
[ ] Invalid credentials show error
[ ] Successful login redirects correctly
[ ] Mobile layout works
[ ] Backend validation exists
```

A task should only be considered complete when its acceptance criteria are satisfied.

# 18. Priority System

PCT V1 uses:

```text
LOW
MEDIUM
HIGH
URGENT
```

---

# 19. LOW Priority

Low priority tasks are useful but not time-sensitive.

Examples:

```text
Minor UI improvement
Optional refactor
Non-critical enhancement
```

---

# 20. MEDIUM Priority

Normal development work.

This should be the default priority when no special urgency exists.

---

# 21. HIGH Priority

Important tasks that should be completed before normal work when practical.

Examples:

```text
Major feature
Important client requirement
Important bug
Deadline-sensitive task
```

---

# 22. URGENT Priority

Critical work requiring immediate attention.

Examples:

```text
Production outage
Critical security issue
Blocking client issue
Major deployment failure
```

Urgent priority should not be abused.

---

Tasks may have a deadline.

# 29. Deadline States

The system may calculate:

```text

Due Soon
Due Today
Overdue
Completed On Time
Completed Late
```

These are derived states and do not necessarily need to be stored as separate database statuses.

---

# 30. Overdue Tasks

A task is overdue when:

```text
Current Time > Deadline
AND
Status != COMPLETED
AND
Status != CANCELLED
```

The system should visually identify overdue tasks.

---

# 31. Deadline Notifications

Where notifications are enabled:

```text
Upcoming Deadline
       ↓
Notification
```

Potential notifications:

```text
24 hours before
Due today
Overdue
```

Exact notification timing should be configurable.

---

# 32. Task Dependencies

Tasks may depend on other tasks.

Example:

```text
Task A
   ↓
Task B
   ↓
Task C
```

Task B cannot be considered ready until Task A is completed.

---

# 33. Dependency Types

PCT V1 may use a simple dependency model:

```text
BLOCKED_BY
```

Example:

```text
Task #20
BLOCKED_BY
Task #15
```

More complex dependency types are optional future functionality.

---

# 34. Circular Dependencies

The system must prevent circular dependencies.

Invalid:

```text
Task A
 ↓
Task B
 ↓
Task C
 ↓
Task A
```

The backend must validate dependency creation.

---

# 35. Blocked Tasks

When a dependency blocks a task:

```text
TODO / IN_PROGRESS
       ↓
BLOCKED
```

The task should display the blocking dependency or reason.

---

# 40. Task Status Transition Rules

Recommended transitions:

```text
BACKLOG
    → TODO
    → CANCELLED

TODO
    → IN_PROGRESS
    → BACKLOG
    → CANCELLED

IN_PROGRESS
    → IN_REVIEW
    → BLOCKED
    → TODO

IN_REVIEW
    → COMPLETED
    → REVISION_REQUIRED

REVISION_REQUIRED
    → IN_PROGRESS

BLOCKED
    → TODO
    → IN_PROGRESS
    → CANCELLED

COMPLETED
    → limited administrative correction only

CANCELLED
    → limited administrative restoration only
```

---

# 41. Status Transition Enforcement

Status changes must be validated by the backend.

The client must not be able to submit:

```json
{
  "status": "COMPLETED"
}
```

and automatically bypass workflow rules.

The backend must determine whether the transition is valid.

---

# 42. Developer Status Changes

Developers may generally change their assigned tasks between:

```text
TODO
IN_PROGRESS
```

and submit:

```text
IN_REVIEW
```

Developers should not normally:

```text
Approve their own review
Force COMPLETED
Cancel arbitrary tasks
Reassign tasks
```

---

# 43. Team Lead Status Changes

Team Leads may manage task workflow within authorized projects.

Typical permissions:

```text

IN_REVIEW

```

Subject to project and review rules.

---

# 44. Admin Status Changes

Admins may manage task status broadly, while still preserving activity history and review integrity.

Administrative overrides should be logged.


# 49. Task Completion

A task becomes `COMPLETED` when:

```text
Acceptance Criteria Met
AND
Required Review Approved
```

If no review is required, an authorized user may complete the task according to project rules.

---

# 50. Reopening Completed Tasks

Completed tasks should not normally be edited back into active work casually.

If reopening is required:

```text
COMPLETED
    ↓
Reopen
    ↓
IN_PROGRESS
```

The action should require appropriate permission and generate an Activity Log entry.

---

# 51. Cancelled Tasks

Cancellation must preserve:

```text
Task
Task History
Comments
Files
Activity
Review History
```

Do not hard-delete a cancelled task simply because it is no longer active.

---

# 52. Task Deletion

Hard deletion should be restricted.

Prefer:

```text
Archive
Cancel
Soft Delete
```

over permanent deletion.

If permanent deletion is implemented, it must require explicit authorization.

---

# 53. Soft Deletion

If soft deletion is used, the task may contain:

```text
deleted_at
deleted_by
```

Deleted tasks should not appear in normal task lists.

Historical activity should remain intact where required.

# 95. Task State Machine

The backend should treat statuses as a state machine.

Conceptually:

```text
BACKLOG
   │
   ▼
TODO
   │
   ▼
IN_PROGRESS
   │
   ▼
IN_REVIEW
   ├──────────────► COMPLETED
   │
   ▼
REVISION_REQUIRED
   │
   └──────────────► IN_PROGRESS
```

Additional branch:

```text
IN_PROGRESS
   ↓
BLOCKED
   ↓
IN_PROGRESS
```

# 96. No Arbitrary Status Changes

Do not allow clients to submit any status combination.


should normally be rejected unless an explicit administrative workflow allows it.
