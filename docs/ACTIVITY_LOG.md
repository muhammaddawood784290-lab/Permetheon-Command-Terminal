# PCT — Activity Log

**Project:** Permetheon Command Terminal
**Short Name:** PCT
**Document Type:** Activity & Audit Log Specification
**Status:** Active
**Version:** 1.0

---

# 1. Purpose

The PCT Activity Log provides a chronological record of important actions performed inside the system.

It is used for:

* Accountability
* Operational visibility
* Debugging
* Task history
* Project history
* Developer activity tracking
* Administrative auditing
* Understanding changes made to system records

The activity log is an internal audit trail.

---

# 2. Core Principle

Important system actions should create an activity record.

Example:

```text
Developer
    ↓
Changes Task #102
    ↓
Activity Record
    ↓
"Task status changed from IN_PROGRESS to REVIEW"
```

Activity records should be generated by the backend.

The frontend must not be trusted to decide whether an audit event should exist.

# 5. What Should Not Be Logged

Do not create excessive activity records for insignificant frontend interactions.

Do NOT log every:

* Button click
* Page visit
* Mouse movement
* UI state change
* Modal opening
* Dropdown opening
* Search keystroke
* Temporary frontend state update

The activity system is an operational audit trail, not an analytics tracker.

Recommended database table:

```text

```

Suggested fields:

```text

entity_id
description
metadata

```

Optional fields may include:

```text
ip_address

```

---

# 7. Field Definitions

## id

Unique activity record identifier.

Type:

```text
BIGINT / INT
```

Primary key.

---

## user_id

The user who performed the action.

Example:

```text
user_id = 17
```

This should reference the users table.

For system-generated events where no direct user exists, this may be nullable.

---

## action

Machine-readable action identifier.

Examples:

```text
TASK_CREATED
TASK_ASSIGNED
TASK_STATUS_CHANGED
PROJECT_CREATED
USER_CREATED
FILE_UPLOADED
```

Action values should remain consistent.

Do not store random free-form action names.

---

## entity_type

Identifies the resource affected.

Examples:

```text
USER
PROJECT
TASK
COMMENT
REVIEW
FILE
NOTIFICATION
```

---

## entity_id

Identifies the affected record.

Example:

```text
entity_type = TASK
entity_id = 102
```

This means:

```text
Task #102
```

---

## description

Human-readable description of the action.

Example:

```text
"Changed task status from IN_PROGRESS to REVIEW."
```

Descriptions should be understandable when shown in the Activity UI.

---

## metadata

Optional structured information about the event.

Example:

```json
{
  "oldStatus": "IN_PROGRESS",
  "newStatus": "REVIEW"
}
```

Metadata may be stored as JSON where supported.

Do not use metadata as a replacement for proper relational fields.

---

## created_at

Timestamp when the activity occurred.

This must be generated server-side.

Do not rely on the frontend timestamp.

# 9. Activity Creation Rules

Activity records must be created on the backend.

Example:

```text
PATCH /api/tasks/:id/status
        │
        ▼
Authentication
        │
        ▼
Permission Check
        │
        ▼
Update Task
        │
        ▼
Create Activity Log
        │
        ▼
Return Response
```

The frontend should never directly insert records into `activity_logs`.

---

# 10. Transaction Consideration

For important database operations, the main database change and activity creation should be treated as one logical operation.

Example:

```text
Task Status Update
       +
Activity Log
```

If the task update fails, the activity should not claim that the update happened.

Where appropriate, database transactions should be used.

---

# 11. Activity Ownership

An activity record contains two important references:

```text
Who performed the action?
        ↓
user_id

What was affected?
        ↓
entity_type + entity_id
```

Example:

```text
user_id = 5
entity_type = TASK
entity_id = 100
action = TASK_ASSIGNED
```

# 12. Activity Visibility

Activity visibility depends on the user's role and the resource involved.

### ADMIN

Can view broad system activity.

May access:

* User activity
* Project activity
* Task activity
* File activity
* Review activity
* Authentication activity

### TEAM_LEAD

Can view activity related to:

* Their projects
* Their teams
* Relevant tasks
* Relevant reviews

### DEVELOPER

Can view:

* Their own activity
* Activity related to tasks they can access
* Relevant project activity

Developers should not automatically receive access to sensitive administrative activity.

# 14. Pagination

Activity logs can grow continuously.

The API must support pagination.

Example:

```text
GET /api/activity?page=1&limit=25
```

Recommended default:

```text
page = 1
limit = 25
```

The backend should prevent unreasonable limits.

# 15. Sorting

Activity logs should normally be sorted newest first.

Default:

```text
created_at DESC
```

Example:

```text
10:45 PM
10:31 PM
10:17 PM
09:52 PM
```

The newest activity appears first.

# 24. Activity Immutability

Activity records should generally be immutable.

Normal users must not be able to:

* Edit activity records
* Change timestamps
* Change the actor
* Change action type
* Change the affected entity

Deletion should be restricted to administrative/system-level maintenance if ever required.

The default behavior is:

```text
Create → Preserve
```

---

# 25. Activity Integrity

The system must not allow users to fabricate activity history.

For example, the frontend must not be able to submit:

```json
{
  "user_id": 1,
  "action": "TASK_APPROVED"
}
```

and create an approval record.

Instead, the backend determines:

```text
Authenticated User
+
Actual Operation
=
Activity Record
```

---

# 26. Security

Activity logs may contain operationally sensitive information.

Therefore:

* Access must be authenticated.
* Role permissions must be enforced.
* Sensitive metadata must not be exposed unnecessarily.
* Passwords must never be logged.
* Authentication secrets must never be logged.
* Database credentials must never be logged.
* Tokens must never be logged.
* Sensitive request payloads must not be copied blindly into metadata.

---

# 27. Performance

Activity logs may become large over time.

The database should index fields commonly used for filtering and sorting.

Recommended indexes may include:

```text
user_id
action
entity_type
entity_id
created_at
```

The exact indexes should be finalized in `DATABASE.md`.

Queries must use pagination.

The application must not load the entire activity table into the frontend.

---

# 28. Activity Retention

PCT activity records are intended to provide long-term operational history.

The default policy is:

```text
No automatic deletion.
```

If a retention policy is introduced later, it must be documented and approved before implementation.

---

# 29. Activity Logging Helper

The backend should use a centralized activity logging mechanism.

Example conceptual interface:

```text
logActivity({
    userId,
    action,
    entityType,
    entityId,
    description,
    metadata
})
```

This is a conceptual pattern.

The exact implementation may vary, but activity creation should not be duplicated unnecessarily throughout controllers.

# 34. Activity Naming Convention

Action names must use a consistent uppercase convention.

Recommended:

```text
RESOURCE_ACTION
```

Examples:

```text
TASK_CREATED
TASK_UPDATED
TASK_ASSIGNED
TASK_STATUS_CHANGED

PROJECT_CREATED
PROJECT_UPDATED

USER_CREATED
USER_UPDATED

FILE_UPLOADED
FILE_DELETED
```

Avoid inconsistent names such as:

```text
taskCreated
created_task
TaskCreated
task-create
```

---

# 35. Activity Description Convention

Descriptions should be:

* Human-readable
* Short
* Specific
* Past-tense
* Useful without opening the related record

Good:

```text
Ahmed changed task status from IN_PROGRESS to REVIEW.
```

Bad:

```text
Task updated.
```

The description should provide enough context to understand what happened.

---

# 36. Activity vs Application Logs

These are two separate systems.

### Activity Log

Business/user actions:

```text
Ahmed assigned Task #104.
```

Stored in:

```text
activity_logs
```

### Server Log

Technical events:

```text
Database connection failed.
```

Handled by:

```text
logger.js
```

Do not mix technical server logs with user-facing activity logs.

---

# 37. Activity vs Notifications

Activity and notifications are also different.

### Activity

Answers:

> What happened?

Example:

```text
Ahmed changed Task #104 to REVIEW.
```

### Notification

Answers:

> What do I need to know?

Example:

```text
Task #104 is ready for your review.
```

One event may create both:

```text
Activity Log
+
Notification
```

but they remain separate records and systems.

# 41. Source of Truth

This document defines how activity and audit logging should work throughout PCT.

`ACTIVITY_LOG.md` must be consulted before implementing:

* Activity pages
* Audit history
* Task history
* Project history
* User activity
* Activity API
* Activity database operations

The activity system must remain centralized, secure, meaningful, and backend-controlled.

**PCT Activity Principle:**

> **If an important action happened, PCT should be able to tell who did it, what happened, what was affected, and when it happened.**
